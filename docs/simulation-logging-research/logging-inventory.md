## 4. Reverse proxy: observed implementation

**C:** `code/integration_layer/server.py` runs two `ThreadingHTTPServer` listeners on localhost 9000 and 9001. `Proxy.handle_request` maps `/v1/models` to `i_am_deepseek` and `/v1/chat/completions` to `human_completion`. The latter prints the first system and user messages, reads terminal input, and returns a fabricated OpenAI-compatible response. | HTTP request path/status via inherited server logging | Console access diagnostics may occur; no custom durable access-log file. |
| Incoming body, messages, requested `model`; returned human text | **A**, available in handler; no persisted request/response record. |

## 8. Minimum additional data, organized by priority

P0 = necessary to interpret the main comparison; P1 = necessary for the selected social/behavioral hypothesis; P2 = optional diagnosis. These are project recommendations, not official benchmark requirements.

| Priority | Retain/reuse first | Truly additional record, if needed | Why / avoid |
| --- | --- | --- | --- |
| P0 | Existing `params.json,memory_config.json`, agent/genome logs, selected audit IDs/scores/reasons, world events, usage | One small run manifest: run ID, parent/submodule SHAs, launcher, condition + resolved config hash, scenario/dataset revision, seed, model/backend/provenance, embedding identity, prompt/template revision, time mapping, checkpoint/resume lineage. Store references once. | Distinguishes the two TerraLingua versions and mock responses; config files alone miss code/backend provenance. |
| P0 | Existing retrieval `event_id,tick,selected,rows` and decision action | Evaluation-side query/sample ID and mapping from agent-local memory ID to original session/turn/event IDs; ordered retrieved IDs at requested K; final `prediction/hypothesis`; evaluator/version/label. | External benchmark adapters/results, not universal simulation instrumentation. Current K=3 cannot report official top-5/top-10 results without a separate chosen retrieval protocol. |
| P0 | Existing candidate scores for small controlled memory studies | Gold relevant/forbidden IDs, expected constraints/answers, admissible evidence, trial/time-gap/rehearsal schedule. **L**, supplied by dataset or independent annotators. | Necessary for Recall@K, appropriateness and correctness. “Rescued” is not a gold label. |
| P0 | Existing world outcome events and fork receipts where applicable | Older wrapper path only: concise decision→outcome join for actions scored by a hypothesis, with executed/refused/unknown and event reference. Structured fallback/parse-failure flag if failed decisions enter denominators. | Avoid a universal full-world snapshot. Newer fork already has selection IDs/receipts, though effects can remain unknown. |
| P1 | Incoming message dictionaries, outgoing text, artifact payload/version/use records | Only if exact diffusion paths are required: stable message/fact ID, sender/recipient tags, send/receive tick/channel and parent transmission/evidence reference; compact successful-knowledge probe result. | Raw text alone cannot distinguish exposure, recall, belief, or paraphrased propagation; first derive exposure where existing logs suffice. |
| P1 | Existing interaction events and fork social topology | Human-labeled relationship expectations, evidence and validity interval; probe responses tied to dyad/tick. **L**. | Follow edges and gifts are measurable; trust/friendship/consistency require operational definitions. |
| P1 | Existing agent/world excerpts for anonymized rating packets | Separate ratings table: packet/sample ID, blinded order, pseudonymous rater ID, rubric version, score/preference, uncertainty and evidence comment. **L**. | No new prompts or memory dumps needed for raters. Keep condition-key separately. |
| P2 | Existing usage records and optional console timing | Per-request attempt/error/latency and correlation ID only for a cost/latency or transport hypothesis. | Not needed to answer the stated believability question by default. |

**Minimize storage and write overhead:** preserve current raw evidence before changing future retention policy. For future evaluation exports, keep one memory-text/metadata table and reference IDs; one resolved config/template per run; one canonical agent-step record. Avoid re-saving full prompts in both agent log and audit, every memory's text/routes on every tick, and full embedding/store snapshots as extra evaluation logs. Current audit already has those duplicates and `_dump_hou_memory` rewrites the whole store every tick ([MA](https://github.com/bloohunnits/human-like-agent-simulation/blob/a178148cab443e69ac599ae3f92509774b5e45e0/code/hou_memory/memory_agent.py) [ME](https://github.com/bloohunnits/human-like-agent-simulation/blob/a178148cab443e69ac599ae3f92509774b5e45e0/code/hou_memory/associative_memory.py)). Keep synchronization/checkpoints required for recovery; propose a separate compact evaluation export rather than silently weakening recoverability. For mechanistic Hou/Honda-style score analysis, retain all candidate scores in the small controlled dataset; for routine simulation, selected candidates plus limited diagnostic samples are enough. No source change was made.

## 9. Questions for teammates and human verification

1. Which launcher and exact commits generated each existing run: parent make target, older Hou wrapper, fork CLI, or unpublished launcher? Provide a raw run folder with agent/world/audit/config/usage files and any resume history for inspection, without rerunning anything.
2. Are the two localhost ports still the terminal-human mock, or is there another forwarding proxy/backend? Which real model, settings, human interventions and usage source were used?
3. Is there unpublished live ACT-R or pure vector implementation? The current launcher offers neither. Which comparison definition and matched budgets should be preregistered?
4. Which LoCoMo-Plus release/unified construction seed and original LongMemEval variant (S/M/oracle; cleaned revision) should be used? LongMemEval-V2 is a separate choice, not an automatic replacement.
5. Which exact Hou appendices/task assets and Honda full text/official implementation are intended? Honda publisher access returned HTTP 403 in this review; local notes are not independently verified requirements.
6. Which Shachi tasks are intended? It is a suite/framework, not one universal metric. A TerraLingua adaptation must be named as a custom Shachi-style evaluation.
7. What are the gold relevant/forbidden memories and the expected action/constraint for each custom probe? Can independent annotators label these before seeing condition outputs?
8. Which social claims matter: acquaintance, reciprocal help, promise keeping, follow topology, or trust? Who establishes changing relationship ground truth?
9. Does “spread” mean delivered text, retained knowledge, correct answer, or subsequent use? Which fact IDs and exposure rules define the denominator, and how will paraphrases be labeled?
10. Are raw logs complete across failures/deaths/resumes, and is the old reduced-log message mismatch affecting existing Anthropologist results? Check sidecar exclusion and graph-world log selection before combining tools.
11. Who will perform blinded ratings, with which rubric, randomization, uncertainty option, and independent coding? Decide sample size through a pilot/analysis plan; no benchmark-mandated number is claimed.
